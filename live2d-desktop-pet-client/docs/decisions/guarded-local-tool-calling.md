# 延后式受保护本地工具调用设计

## 背景

当前 MVP 只定义 Java AI 后端和 Tauri/Vue 桌宠客户端之间的 WebSocket 语义协议。真实本地工具执行延后到 MVP 之后。MVP 阶段，`tool.request` 只表达后端想让客户端发起一个受保护的本地动作，客户端只能让用户确认或拒绝，并通过 `tool.confirmed` 或 `tool.rejected` 回传结果。

这份设计描述后续启用本地工具执行时的权限边界。它不是实现计划，也不改变当前协议验证范围。

## 设计目标

1. 后端只做意图规划，不做本地执行。
2. 客户端本地执行层默认拒绝所有工具。
3. 每次有风险的工具调用都需要用户明确确认。
4. 权限、确认、审计事件都用可追踪的 `toolCallId` 关联。
5. 初始工具集只包含低风险动作，不包含 shell、文件删除、文件覆盖、进程管理等能力。

## 相关模块和调用方地图

1. Java AI 后端，负责对话规划和语义意图。它可以发送 `assistant.message.delta`、`pet.expression`、`pet.motion`、`tool.request`。它不能直接操作用户本机。
2. WebSocket 语义协议，定义 `tool.request`、`tool.confirmed`、`tool.rejected`、`error`。协议只传递语义，不传递 Tauri 命令名、系统路径、shell 命令或渲染器细节。
3. Tauri/Vue 桌宠客户端，负责展示桌宠、对话流、工具确认界面和本地权限判断。未来的本地执行只能发生在客户端受控边界内。
4. 聊天面板，未来承接工具请求的用户可见入口。它把后端意图转成可确认的本地动作说明，并保持对话不中断。
5. 本地工具守卫，未来新增的客户端内部模块。它先检查工具名、参数、风险等级、用户授权和会话状态，再决定拒绝、请求确认或执行。
6. 确认面板状态机，未来新增的客户端 UI 状态。它管理待确认、已拒绝、已确认、超时、执行跳过和未来执行结果。
7. 审计事件记录器，未来新增的客户端内部模块。它记录工具请求、权限判断、用户选择、执行结果和错误原因，供用户和开发者排查。

## 后端规划和本地执行边界

后端发送的是意图，不是命令。比如后端可以请求 `open_url`，并给出待打开的 URL 和面向用户的说明。后端不能要求客户端运行 `cmd`、`powershell`、`bash`、删除文件、写入任意路径或启动任意程序。

客户端是唯一可以接触本机能力的一侧。即使后端发送了格式正确的 `tool.request`，客户端也必须重新做本地 allowlist 校验。后端的 `requiresConfirmation: true` 不是授权，只是协议声明。真正的授权来自客户端策略和用户确认。

## 权限和风险等级

1. 低风险，动作可见，影响可逆或影响范围很小。例子是打开 HTTPS 网页、复制文本到剪贴板、显示系统通知。低风险工具仍默认需要用户确认，除非用户之后在设置里给某个工具开启明确的记住授权。
2. 中风险，可能改变用户环境或暴露少量本地信息。例子是打开本地文件选择器、读取用户主动选择的单个文件、创建日历提醒。中风险工具必须逐次确认，确认界面要展示参数摘要。
3. 高风险，可能造成数据损失、隐私泄露或系统状态变化。例子是写文件、覆盖文件、启动外部程序、访问目录树、网络上传本地内容、执行 shell。高风险工具不进入初始工具集。后续如果引入，必须有单独设计、开关、审计和更强确认。

默认策略是 deny by default。任何未知工具名、未知参数、缺少 `toolCallId`、缺少 `requiresConfirmation: true`、参数校验失败、风险等级缺失的请求，都直接拒绝，并发送 `tool.rejected`，`reason` 使用 `permission_denied`。

## Allowlist 结构

每个允许的工具需要有一条客户端本地 allowlist 记录。

```json
{
  "tool": "open_url",
  "risk": "low",
  "requiresConfirmation": true,
  "argumentSchema": "https_url_only",
  "audit": true
}
```

allowlist 只存在于客户端本地代码或受信配置中。后端不能下发 allowlist，也不能提升风险等级。协议版本升级时，新增工具必须先进入文档和测试，再进入客户端 allowlist。

## 确认流程

1. 客户端收到 `tool.request`。
2. 本地工具守卫检查协议 envelope、`toolCallId`、工具名、参数结构、风险等级和 allowlist。
3. 校验失败时，客户端不展示确认弹窗，直接发送 `tool.rejected`，`reason` 为 `permission_denied`，并写入审计事件。
4. 校验通过时，客户端展示确认界面。界面需要显示工具名称、风险等级、后端说明、关键参数和取消选项。
5. 用户确认后，MVP 只发送 `tool.confirmed`。真实执行仍保持延后。MVP 之后，客户端才可以在确认后进入本地执行层。
6. 用户拒绝或确认超时后，客户端发送 `tool.rejected`，`reason` 为 `user_rejected` 或 `timeout`。

确认界面不能把后端文案当成唯一依据。客户端需要用自己的模板说明将要发生的本地动作。例如 `open_url` 要展示完整域名和协议。

## 前端确认面板状态

工具调用应该表现为聊天面板里的受保护动作卡片，而不是系统级弹窗优先。系统弹窗只适合后续真实执行需要操作系统权限时使用。

1. `hidden`，没有待处理工具请求。
2. `policy_denied`，本地策略拒绝。用户可以看到简短说明，但不看到确认按钮，避免误以为还能授权。
3. `awaiting_user`，等待用户确认。卡片展示工具名、风险等级、参数摘要、后端说明、确认按钮、拒绝按钮和倒计时。
4. `confirmed_deferred`，用户已确认，但当前计划仍延后真实执行。卡片说明已把确认结果发给后端，没有执行本机动作。
5. `rejected`，用户拒绝。卡片保留在消息流中，说明没有执行动作。
6. `expired`，用户没有及时选择。卡片禁用按钮，并发送 `tool.rejected`。
7. `executing`，未来启用真实执行后使用。MVP 和当前前端优先阶段不进入这个状态。
8. `completed` 或 `failed`，未来真实执行结果。当前只作为审计和历史面板预留。

确认卡片必须能从聊天上下文里看懂。用户不应该需要打开开发日志才知道哪个请求被确认、拒绝或跳过。

## 前端用户约束

1. 同一时间只展示一个高优先级确认焦点。多个 `tool.request` 到达时，客户端应排队或拒绝后续请求，避免按钮选择对应错请求。
2. 确认按钮文案必须描述动作，例如打开网页，而不是只写允许。
3. 参数摘要必须由客户端生成。`open_url` 至少展示协议、域名和完整 URL 的可展开视图。
4. 拒绝必须和确认一样容易点击。倒计时结束按拒绝处理。
5. `toolCallId` 不展示为主要文案，但可以在调试详情或历史面板里出现。
6. 真实执行延后期间，卡片必须明确写出不会执行本机动作，只会回传用户选择。

## 审计事件

审计事件先按本地开发日志设计，后续可以接入用户可见的历史面板。每条事件都包含 `toolCallId`、时间、来源会话、工具名、风险等级和结果。

建议事件类型如下。

1. `tool.request.received`，收到后端工具请求。
2. `tool.policy.denied`，本地策略拒绝请求。
3. `tool.confirmation.shown`，已向用户展示确认。
4. `tool.confirmation.accepted`，用户确认。
5. `tool.confirmation.rejected`，用户拒绝或超时。
6. `tool.execution.skipped`，当前 MVP 或禁用状态下跳过真实执行。
7. `tool.execution.completed`，未来真实执行成功。
8. `tool.execution.failed`，未来真实执行失败。

MVP 阶段最重要的是记录 `tool.execution.skipped`，避免误以为 `tool.confirmed` 已经代表本机动作完成。

## 初始低风险工具集

初始工具集只建议包含以下低风险工具，并且在 MVP 之后才启用真实执行。

1. `open_url`，打开 HTTPS URL。只允许 `https://`，禁止 `file://`、`javascript:`、自定义协议和内网地址策略需另行评估。MVP 当前协议已经只允许这个工具。
2. `copy_text`，复制后端生成的短文本到剪贴板。需要展示文本预览和长度。该工具不在当前协议 allowlist 内，后续新增前需要更新协议和 schema。
3. `show_notification`，展示桌面通知。需要限制标题和正文长度。该工具不在当前协议 allowlist 内，后续新增前需要更新协议和 schema。

初始工具集明确不包含 shell 执行、文件删除、文件覆盖、目录扫描、任意文件读取、任意程序启动、注册表修改、系统设置修改。

## MVP 约束

当前批准计划继续延后真实本地工具执行。MVP 可做的事情只有协议层确认闭环。

1. 后端发送 `tool.request`。
2. 客户端校验并请求用户确认。
3. 客户端发送 `tool.confirmed` 或 `tool.rejected`。
4. 客户端记录审计事件。
5. 客户端不执行真实本地动作。

前端优先阶段可以先完成确认卡片、状态文案、超时和拒绝路径的体验草图。不要在这个阶段接入 Tauri 命令、shell、文件系统或真实本地执行。

如果未来启用执行，需要先补齐客户端本地工具守卫、allowlist、确认 UI、审计事件、协议 schema、单元测试和手动 QA。
