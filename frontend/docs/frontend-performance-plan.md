# 前端性能优化计划

## 目标

优化前端在频繁切换组件、重复进入聊天页、频繁展示图片资源时的 CPU、网络和渲染开销。优先保证体验稳定，其次再考虑更激进的缓存策略。

## 优化范围

### 1. WebSocket / STOMP 连接复用

- 连接保持单例复用，不随组件频繁挂载/卸载立刻断开。
- 组件卸载时只做本地状态清理，不立即 close 底层连接。
- 连接空闲后延迟关闭，默认建议 **30 秒**，可根据实际体验调整到 20–30 秒区间。
- 若在延迟窗口内有新组件重新进入，则取消关闭定时器并继续复用现有连接。

### 2. 图片缓存

- **会变的图**（头像、用户刚上传的图）采用“同一个业务 id 覆盖同一份缓存”的策略，避免不断新增 key。
- **稳定图**（Live2D 静态资源、背景图、生成型图片）允许缓存复用。
- 生成型图片建议按 `imageId` / `resourceId` / `promptHash` 做 key，并配 TTL。

### 3. 音频与消息流的轻量缓存

- 流式文本消息保留短期内的本地状态，避免组件切换时重复拉取。
- 音频播放状态与分片处理继续走已有播放器 composable，不额外把大块音频缓存到长期内存。

## 推荐策略

| 类别 | 策略 | 原因 |
| --- | --- | --- |
| WebSocket 连接 | 延迟关闭 20–30 秒，推荐 30 秒 | 兼顾频繁切换和资源占用 |
| 头像等会变资源 | 同 key 覆盖 + 短 TTL | 防止缓存膨胀，避免内存爆炸 |
| 生成型图片 | 稳定 key + 可缓存 | 重复展示收益高，适合复用 |
| 流式消息 | 页面内短期缓存 | 减少重复请求和闪动 |
| 音频数据 | 不长期缓存大块数据 | 避免内存压力 |

## 场景

### Happy path

- 用户在聊天页、首页、回忆页之间频繁切换，WebSocket 不反复重连。
- 同一张头像或生成图重复展示时，前端直接复用缓存。

### Edge

- 用户快速打开 / 关闭聊天组件，多次切换后仍然只维持一条连接。
- 头像更新后，旧缓存被覆盖，不会累计成多个副本。

### Regression

- 延迟关闭不应导致“已离开页面但连接永久不释放”。
- 图片缓存不应把会变资源长期保留成旧版本。

## 分阶段执行

### Phase 1 — WebSocket 延迟关闭

- 抽象出连接生命周期管理。
- 组件销毁时改为延迟断开，而不是立刻 disconnect。
- 增加重新进入时取消断开定时器的逻辑。

### Phase 2 — 图片缓存

- 为头像、背景图、生成图设计一致的 key 规则。
- 会变资源采用覆盖式缓存。
- 稳定资源允许复用并设置 TTL。

### Phase 3 — 回归验证

- 验证频繁切换组件时 CPU 和连接次数下降。
- 验证头像更新后不再读取旧缓存。
- 验证生成型图片能稳定复用。

## 不做的事

- 不把大块音频做长期缓存。
- 不把所有图片都无差别永久缓存。
- 不为了缓存引入复杂的多层状态管理。

## 成功标准

- WebSocket 不再因组件切换频繁断连重连。
- 图片缓存不会无限膨胀。
- 频繁切换页面时 CPU 和网络抖动明显下降。
